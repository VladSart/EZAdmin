# Exchange Hybrid GAL Split (Cloud ↔ On-Prem Recipient Visibility) — Hotfix Runbook (Mode B: Ops)
> Fix or escalate in under 10 minutes.
> Covers: an Exchange Online mailbox that on-prem users can't find in the GAL / OAB (or that doesn't show in the on-prem EAC), on-prem mailboxes missing from the cloud GAL, `RemoteMailbox` objects with an empty/mismatched `ExchangeGuid`, cloud-only mailboxes created directly in EXO in a hybrid org, and hidden-from-GAL flags that disagree between the two sides.
> Deep dive: `HybridGALSplit-A.md` · Script: `Scripts/Get-HybridRecipientVisibilityAudit.ps1`
> Not this runbook: single-directory GAL/OAB lag, ABPs, IMCEAEX → `AddressBook-OAB-B.md`. Connector/free-busy/OAuth → `Hybrid-Coexistence-B.md`. Sync engine errors → `EntraID/` Connect/Cloud Sync runbooks.

## Triage

The core rule: **in a hybrid org, the on-prem AD is the address book source for everyone.** On-prem users' GAL/OAB is built from on-prem AD; EXO's GAL is built from what Entra Connect syncs up. A cloud mailbox only appears on-prem if an on-prem AD object with Exchange attributes (`RemoteMailbox`) represents it.

**On-prem** — Exchange Management Shell (or the Exchange Management Tools recipient snap-in if the last server is gone):
```powershell
$u = "<user@contoso.com>"
Get-Recipient $u -ErrorAction SilentlyContinue | Format-List Name,RecipientTypeDetails,HiddenFromAddressListsEnabled,ExternalEmailAddress
Get-RemoteMailbox $u -ErrorAction SilentlyContinue | Format-List ExchangeGuid,RemoteRoutingAddress,HiddenFromAddressListsEnabled
Get-User $u | Format-List RecipientType,RecipientTypeDetails,UserPrincipalName
```
**Cloud** — `Connect-ExchangeOnline -Prefix Cloud` (prefix avoids cmdlet collisions with the on-prem session; `Get-EXO*` cmdlets are not prefixed):
```powershell
Get-EXOMailbox $u -Properties ExchangeGuid,IsDirSynced,HiddenFromAddressListsEnabled | Format-List RecipientTypeDetails,ExchangeGuid,IsDirSynced,HiddenFromAddressListsEnabled
```

| Observation | Meaning | Go to |
|---|---|---|
| EXO mailbox `IsDirSynced : True`, on-prem `Get-User` shows `RecipientType : User` (no Exchange attributes) | User was licensed in the cloud before anyone ran `Enable-RemoteMailbox`. Mailbox exists, but on-prem has no recipient → invisible in on-prem GAL/EAC, mail from on-prem users may NDR | Fix 1 |
| On-prem `RemoteMailbox` exists, `ExchangeGuid : 00000000-0000-0000-0000-000000000000` or differs from EXO | GUID not stamped/mismatched. GAL works but **move-back (offboarding) fails** and Entra Connect can't link the mailbox correctly | Fix 2 |
| EXO mailbox `IsDirSynced : False` in a hybrid org | Created as cloud-only (e.g. shared mailbox created in EXO admin center). On-prem has no object at all → invisible to on-prem users | Fix 3 |
| `HiddenFromAddressListsEnabled` differs between on-prem and cloud | On-prem is SOA for synced objects; cloud value is overwritten each sync cycle | Fix 4 |
| On-prem mailbox missing from **cloud** GAL; `Get-EXORecipient` returns nothing | Object not syncing (OU filter / sync error) — not a GAL problem | Fix 5 |
| Everything matches, recipient visible in OWA but not classic Outlook | OAB lag on whichever side the *viewer's* mailbox lives | `AddressBook-OAB-B.md` Fix 1 |

## Dependency Cascade
<details><summary>What must be true</summary>

```
Viewer sees recipient in GAL/OAB
└── Viewer's mailbox location decides the address book source
    ├── Viewer ON-PREM → on-prem AD GAL + on-prem OAB (generated by arbitration mbx, default daily)
    │   └── Recipient must exist in on-prem AD as a mail-enabled object
    │       ├── Cloud mailbox → RemoteMailbox (msExchRecipientTypeDetails = RemoteUserMailbox/RemoteSharedMailbox/...)
    │       │   ├── RemoteRoutingAddress = alias@<tenant>.mail.onmicrosoft.com (targetAddress)
    │       │   └── ExchangeGuid = EXO mailbox ExchangeGuid (needed for move-back + clean linking)
    │       ├── Not hidden (msExchHideFromAddressLists ≠ TRUE)
    │       └── Stamped into Default GAL (showInAddressBook) by on-prem Exchange recipient policy
    └── Viewer IN EXO → EXO GAL + EXO OAB (~8 h generation, Outlook downloads ~24 h)
        └── Recipient must exist in Entra ID / EXO
            ├── On-prem mailbox → synced by Entra Connect / Cloud Sync → appears as MailUser in EXO
            │   ├── Object in sync scope (OU / attribute filter)
            │   └── No sync error (duplicate proxyAddress / UPN)
            └── Hidden flag sourced from on-prem msExchHideFromAddressLists
```
</details>

## Diagnosis & Validation Flow

1. **Where does the viewer's mailbox live?** `Get-Recipient <viewer>` on-prem → `UserMailbox` = on-prem viewer; `RemoteUserMailbox` = cloud viewer. Diagnose the *viewer's* side's directory.
2. **Does the recipient exist on that side?**
   - On-prem: `Get-Recipient <target>` → expect `RemoteUserMailbox`/`RemoteSharedMailbox`/`RemoteRoomMailbox`. `User`/`MailUser`/not found = Fix 1 or Fix 3.
   - Cloud: `Get-EXORecipient <target>` → expect `MailUser` (for on-prem mbx) or mailbox type. Not found = Fix 5.
3. **GUID check** (cloud mailbox): on-prem `(Get-RemoteMailbox <target>).ExchangeGuid` must equal `(Get-EXOMailbox <target> -Properties ExchangeGuid).ExchangeGuid`. Mismatch/zeros = Fix 2.
4. **Routing check:** `RemoteRoutingAddress` must be `*@<tenant>.mail.onmicrosoft.com` and that address must be in the EXO mailbox's `EmailAddresses`. Wrong → on-prem mail to the user loops/NDRs (`Hybrid-Coexistence-B.md`).
5. **Hidden flag:** compare `HiddenFromAddressListsEnabled` both sides. Fix only on-prem (Fix 4).
6. **Stamped into GAL:** on-prem `Get-Recipient <target> | fl AddressListMembership` — empty = run `Update-Recipient <target>` (on-prem) or wait for OAB regen.
7. **OAB lag:** if 1–6 are clean, it's OAB timing → `AddressBook-OAB-B.md`.

## Common Fix Paths

<details><summary>Fix 1 — Cloud mailbox exists, on-prem user has no Exchange attributes (licensed before Enable-RemoteMailbox)</summary>

On-prem EMS. Get the EXO GUID first (cloud session):
```powershell
$u    = "<user@contoso.com>"
$guid = (Get-EXOMailbox $u -Properties ExchangeGuid).ExchangeGuid
$alias = (Get-EXOMailbox $u).Alias
```
On-prem:
```powershell
Enable-RemoteMailbox -Identity $u -RemoteRoutingAddress "$alias@<tenant>.mail.onmicrosoft.com"
Set-RemoteMailbox    -Identity $u -ExchangeGuid $guid
# Shared mailbox:  Enable-RemoteMailbox ... -Shared   (Exchange 2013 CU21+/2016 CU10+/2019)
# Room mailbox:    Enable-RemoteMailbox ... -Room
Get-RemoteMailbox $u | Format-List RecipientTypeDetails,ExchangeGuid,RemoteRoutingAddress
```
Then force a delta sync on the Entra Connect server: `Start-ADSyncSyncCycle -PolicyType Delta`.
- If `Enable-RemoteMailbox` complains about existing `proxyAddresses`, check the AD user's `proxyAddresses` for conflicts first — don't blank them (it's what the cloud mailbox is using).
- **Rollback:** `Disable-RemoteMailbox <u>` removes on-prem Exchange attributes only — **but** after the next sync, EXO may see `msExchRecipientTypeDetails` change and soft-delete/disconnect the cloud mailbox. Never run it on a live cloud mailbox without a plan.
</details>

<details><summary>Fix 2 — RemoteMailbox ExchangeGuid zero or mismatched</summary>

```powershell
$u = "<user@contoso.com>"
$guid = (Get-EXOMailbox $u -Properties ExchangeGuid).ExchangeGuid   # cloud session
Set-RemoteMailbox $u -ExchangeGuid $guid                              # on-prem
# Archive too, if the cloud mailbox has one:
$aguid = (Get-EXOMailbox $u -Properties ArchiveGuid).ArchiveGuid
if ($aguid -ne [guid]::Empty) { Set-RemoteMailbox $u -ArchiveGuid $aguid }
```
Bulk (all zeros) — export first, review, then apply:
```powershell
Get-RemoteMailbox -ResultSize Unlimited | Where-Object { $_.ExchangeGuid -eq [guid]::Empty } |
  Select-Object UserPrincipalName,RemoteRoutingAddress | Export-Csv .\ZeroGuid.csv -NoTypeInformation
```
Non-destructive; write-back is just an AD attribute. Delta sync afterwards.
</details>

<details><summary>Fix 3 — Mailbox was created cloud-only (IsDirSynced = False) in a hybrid org</summary>

Pick one:
- **Quick visibility only:** create an on-prem mail contact so on-prem users can find/address it:
  ```powershell
  New-MailContact -Name "<Display Name>" -ExternalEmailAddress "<shared@contoso.com>" -OrganizationalUnit "<OU not in sync scope>"
  ```
  The OU **must be excluded** from Entra Connect sync, or the contact syncs up and collides with the cloud mailbox's proxy address.
- **Proper fix (preferred for user mailboxes):** convert to a synced object — create the AD user (in sync scope) with matching UPN/proxyAddresses, `Enable-RemoteMailbox` + `Set-RemoteMailbox -ExchangeGuid` per Fix 1, then let Entra Connect soft-match by SMTP/UPN. Plan it: a soft-match failure creates a duplicate. Test on one object, and confirm soft-match is allowed (`(Get-MgDirectoryOnPremiseSynchronization).Features.BlockSoftMatchEnabled` should be `$false`).
- Going forward: in hybrid, create mailboxes with `New-RemoteMailbox` on-prem (or EAC "Office 365 mailbox"), never in the EXO admin center.
</details>

<details><summary>Fix 4 — Hidden-from-GAL disagrees between on-prem and cloud</summary>

On-prem is source of authority for synced objects. Set it on-prem only:
```powershell
Set-RemoteMailbox <u> -HiddenFromAddressListsEnabled $true    # cloud mailbox
Set-Mailbox       <u> -HiddenFromAddressListsEnabled $true    # on-prem mailbox
```
No Exchange server left? Use the Exchange Management Tools recipient snap-in (same cmdlets). Direct `Set-ADUser <sam> -Replace @{msExchHideFromAddressLists=$true}` works but is unsupported — last resort only.
Then `Start-ADSyncSyncCycle -PolicyType Delta`. Allow OAB regeneration time on both sides.
</details>

<details><summary>Fix 5 — On-prem mailbox missing from the cloud GAL</summary>

```powershell
# Entra Connect server
Get-ADSyncConnectorRunStatus
Import-Module ADSync; Get-ADSyncCSObject -DistinguishedName "<user DN>" -ConnectorName "<contoso.com>"   # in connector space?
```
- Not in connector space → OU/attribute filter. Fix scope, run `Start-ADSyncSyncCycle -PolicyType Initial` only if the scope change requires a full import.
- Export error (e.g. `AttributeValueMustBeUnique` on proxyAddresses) → resolve duplicate per `EntraID/` Connect runbooks.
- Present in EXO as `MailUser` but hidden → Fix 4.
</details>

## 🎓 Learning Pointers
- If Fix 1 was needed, the real defect is the **provisioning process** — someone assigned an Exchange Online licence to a synced user with no `RemoteMailbox`. Hybrid provisioning should always be `New-RemoteMailbox` / `Enable-RemoteMailbox` first. MS Learn: [Create a cloud-based mailbox in hybrid](https://learn.microsoft.com/exchange/hybrid-deployment/create-cloud-based-mailbox).
- The zero `ExchangeGuid` from Fix 2 is invisible day-to-day and only bites when you offboard a mailbox back on-prem or decommission — run the audit script before any Exchange server retirement. Ali Tajran's write-up on [Enable-RemoteMailbox ExchangeGuid](https://www.alitajran.com/enable-remotemailbox-exchangeguid-is-mandatory-on-usermailbox/) walks through the symptoms.
- Hidden-flag "won't stick" tickets (Fix 4) are always SOA: synced attributes are mastered on-prem, and EXO edits are rejected or overwritten.
- Last Exchange server gone? Recipient management continues through the **Exchange Management Tools** recipient snap-in (Exchange 2019 CU12+/SE) — see [Manage recipients in hybrid without Exchange servers](https://learn.microsoft.com/exchange/manage-hybrid-exchange-recipients-with-management-tools).
- Address-book timing after any of these fixes is a separate problem — see `AddressBook-OAB-A.md` for OAB generation/download cadence.
