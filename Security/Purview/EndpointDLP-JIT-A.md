## Scope & Assumptions

**In scope:** Microsoft Purview Endpoint DLP's **just-in-time (JIT) protection** feature — the mechanism that detects and blocks (or audits) egress activities on files that haven't completed DLP policy evaluation yet, closing the timing gap between "user attempts an action" and "DLP finishes classifying the file." Covers the full JIT workflow, prerequisites, fine-tuning settings, and the newer JIT Audit user/group scoping capability.

**Out of scope (covered elsewhere):**
- General Endpoint DLP policy authoring, detection rules, and non-JIT Block/Audit enforcement — see `DLP-Policy-A.md`/`-B.md`.
- The general **File path exclusions for Windows** Endpoint DLP setting (exempts a path from Endpoint DLP entirely) — distinct from JIT's own, narrower file-path-exclusion setting covered here; see `EndpointDLPExcludedFolders-A.md`/`-B.md` for the general-exclusion feature.
- Endpoint onboarding to Microsoft Purview / Defender for Endpoint itself — assumed already complete.

> **Source-confidence note:** the core JIT protection workflow, prerequisites, and antimalware client version requirements below are sourced directly from primary Microsoft Learn documentation (`endpoint-dlp-get-started-jit`, `ms.date` 2026-06-26; `endpoint-dlp-learn-about-jit`, `ms.date` 2026-06-22) and are treated as settled. The newer **JIT Audit user/group scoping** capability (Microsoft 365 Roadmap ID 562991) has **no dedicated Learn conceptual page** as of this writing, and its reported release date is inconsistent across secondary sources — the Roadmap listing itself states General Availability, **July CY2026**, Worldwide Standard Multi-Tenant, while other trade-press coverage reports a September CY2026 GA target. This runbook treats the scoping capability's exact mechanics and current live rollout status as unconfirmed and flags this explicitly rather than guessing at its configuration surface — verify directly against the live Purview portal before presenting it as settled to a client.

**Assumed baseline:** Windows 10/11 or macOS (three most recent versions) devices onboarded to Microsoft Purview Endpoint DLP; Defender antimalware client version `4.18.23080` or later; at least one active Endpoint DLP policy with a Block or Block-with-override action already configured for a monitored egress location.

## How It Works

<details><summary>Full architecture</summary>

### The problem JIT solves

Ordinary Endpoint DLP classification is not instantaneous — a file must be evaluated against active DLP policies before an egress action (copy, print, upload, etc.) can be correctly allowed or blocked. Without JIT, a file that hasn't been classified yet (or whose classification has gone **stale** because the governing policy was updated after the file was last evaluated) is a gap: the system either has to block everything indiscriminately until evaluation completes, or risk letting a sensitive, not-yet-classified file leave unprotected. JIT protection closes this specific timing window.

### Core terminology

- **Stale classification** — a classification produced by an outdated version of a DLP policy; the item remains stale until re-evaluated against the current policy.
- **JIT candidate file** — any file DLP hasn't evaluated yet, or whose classification is stale.
- **JIT audit** — JIT logs an activity-explorer event (`JIT triggered: true`, `Enforcement mode: Audit`) without blocking. No `DLPRuleMatch` event or alert is generated by JIT itself.
- **JIT block** — JIT blocks the activity and logs an equivalent event with `Enforcement mode: Block`.
- **Fallback action in case of failure** — the enforcement mode DLP applies specifically when policy evaluation *doesn't complete* (Allow, the recommended default, vs. Block). This setting is orthogonal to whether JIT itself blocks or audits — it only governs the failure-to-evaluate case.

### The JIT evaluation workflow (single-file activity)

1. A user attempts an egress activity (copy to removable media/network share, print, RDP copy/move, Bluetooth transfer, clipboard copy, or upload to a restricted cloud service) on an onboarded device.
2. If the file/activity matches an excluded app, excluded file path, or excluded file extension, evaluation ends immediately with no JIT event logged and no block.
3. DLP checks whether the user is in the configured **JIT scope**. If not, JIT doesn't block — a JIT **audit** event is logged and the activity proceeds.
4. DLP checks whether any active rule defines Block or Block-with-override for this activity. If not, again JIT audits only, doesn't block.
5. DLP checks whether the destination is an allowed printer/USB group/network share/URL. If so, JIT doesn't block regardless of scope/rule matches.
6. If none of the above short-circuits apply, JIT evaluation triggers in earnest.
7. For activities that support **JIT pause and resume** (copy to removable media, copy to network share): if policy evaluation completes within **3 seconds**, the determined action (audit/block/block-with-override) applies and, for a passing evaluation, the activity automatically resumes with no user action needed.
8. For activities that don't support resume (print, RDP, Bluetooth, clipboard): the user must manually retry the activity after the evaluation-complete notification.
9. If evaluation isn't done within the initial window, JIT allows **two more seconds** (single-file) before applying an interim action; if still incomplete after a total of **5 seconds**, the activity is blocked with a **"Just-in-time in progress"** message, and JIT allows **30 more seconds** for evaluation to finish.
10. If evaluation completes within that 30-second window, the user sees a **"Just-in-time evaluation complete"** message and is prompted to retry. If it still hasn't completed, the configured **fallback action** (Allow/Block) is applied instead.

### Multi-file activity handling

When a user acts on multiple files simultaneously, JIT consolidates notifications rather than firing one toast per file — for resume-capable activities, files completing within 5 seconds auto-resume together; for non-resume activities, files completing within 2 seconds are grouped into a single consolidated "final verdict" toast rather than an interim "in progress" toast per file.

### Why JIT has no independent detection logic

JIT is explicitly **not** a parallel DLP engine — every decision it makes derives from the same underlying Endpoint DLP policy evaluation that would eventually complete anyway. JIT's entire value is in *how it behaves during the gap* before that evaluation finishes, not in evaluating content differently. This is why a tenant with JIT fully enabled but zero Block-capable Endpoint DLP policies will observe no JIT activity at all — correctly, since there's no eventual "real" verdict for JIT to be a stand-in for.

### The JIT Audit user/group scoping capability (Roadmap 562991)

Reported functionality: administrators will be able to explicitly include or exclude specific users or groups from JIT **Audit** logging, so audit events are generated only for the selected population rather than broadly. This is a *reporting-scope* control layered onto the audit side of JIT specifically — it is distinct from the existing overall **JIT scope** setting (which governs whether JIT evaluates a user/device at all, for both audit and block purposes). As of this writing, no primary Microsoft Learn page documents the precise relationship between this new audit-specific scoping and the pre-existing general JIT scope setting — treat the two as likely complementary but unconfirmed in their exact interaction until Microsoft publishes conceptual documentation.

## Dependency Stack

```
Layer 5: JIT Audit user/group scoping (Roadmap 562991 — GA date disputed across sources,
           July vs September CY2026; no primary Learn page as of this writing)
           - narrows WHICH users generate JIT Audit events specifically
Layer 4: JIT fine-tuning settings
           - Fallback action in case of failure (Allow/Block on evaluation timeout)
           - Control copying to clipboard (off by default; clipboard is Audit-only until enabled)
           - App exclusions (Windows/Mac, max 50 each) — JIT-specific, distinct from general DLP app lists
           - File extension exclusions
           - File path exclusions (Windows/Mac) — JIT-specific; narrower than the general
             "File path exclusions for Windows" Endpoint DLP setting
Layer 3: JIT protection enabled for Devices location + JIT scope (which users/devices JIT evaluates)
           (Purview portal > Settings > Data Loss Prevention > Just-in-time protection)
Layer 2: Defender antimalware client version gate
           4.18.23080+ required for JIT to function at all
           4.18.25080+ required for the improved in-progress/evaluation-complete toast UX
Layer 1: Active Endpoint DLP policy with Block or Block-with-override action
           for the specific egress activity — JIT has NOTHING to enforce without this
```

A device sitting below the Layer 2 version floor is functionally outside JIT entirely, regardless of how Layers 3-5 are configured — always check this first in any JIT troubleshooting sequence.

## Symptom → Cause Map

| Symptom | Most Likely Cause | Check |
|---------|-------------------|-------|
| JIT appears completely inactive on a specific device | Antimalware client below `4.18.23080` | Advanced Hunting `DeviceRegistryEvents` query against `MsMpEng.exe` version |
| JIT active but missing the in-progress/evaluation-complete toast notifications | Antimalware client between `4.18.23080` and `4.18.25079` — functional but pre-UX-improvement | Same query, compare against `4.18.25080` |
| No JIT events logged anywhere despite JIT being enabled | No active Endpoint DLP policy has a Block/Block-with-override rule for any monitored activity | `Get-DlpComplianceRule` filtered to Endpoint workload |
| File in an "excluded" folder still evaluated by ordinary DLP (just not JIT-blocked) | JIT-specific file path exclusion was configured, mistaken for the general Endpoint DLP path exclusion — by design, JIT path exclusion only skips JIT, not full DLP evaluation | Compare which of the two distinct exclusion settings is actually populated |
| Clipboard copy suddenly blocked, not just audited | "Control copying to clipboard" toggled on — clipboard is Audit-only by default | Check the Additional settings toggle state |
| Reported JIT block doesn't match the documented 5-second/30-second timing model | Activity type doesn't support JIT pause/resume (print, RDP, Bluetooth, clipboard) and is being judged against resume-capable timing expectations | Confirm activity type against the two documented timing tracks |
| Setting change (scope, exclusions, enable/disable) appears not to have taken effect | Propagation window (up to 1 hour) not yet elapsed | Re-check after confirmed elapsed time |
| New JIT Audit scoping setting behaves inconsistently with the general JIT scope setting | Undocumented interaction between the two scoping layers (Roadmap 562991 has no primary Learn page yet) | Flag as an open question; do not assume a specific precedence without direct portal verification |

## Validation Steps

1. **Confirm antimalware client version fleet-wide.**
   ```kusto
   DeviceRegistryEvents
   | where InitiatingProcessVersionInfoInternalFileName == "MsMpEng.exe" and Timestamp >= ago(60d)
   | summarize arg_max(Timestamp, *) by DeviceId
   | distinct DeviceName, DeviceId, AntiMalwareClientVersion = InitiatingProcessVersionInfoProductVersion
   | summarize dcount(DeviceId) by AntiMalwareClientVersion
   | order by dcount_DeviceId desc
   ```
   *Good:* majority at `4.18.23080`+ (ideally `4.18.25080`+). *Bad:* significant population below floor — those devices are silently outside JIT coverage.

2. **Confirm at least one Block-capable Endpoint DLP policy exists.**
   ```powershell
   Get-DlpCompliancePolicy | Where-Object { $_.Workload -match "Endpoint" -and $_.Enabled -eq $true }
   Get-DlpComplianceRule | Where-Object { $_.BlockAccess -eq $true -or $_.BlockAccessScope }
   ```
   *Good:* at least one enabled rule with Block/Block-with-override targeting a monitored activity. *Bad:* none — JIT has nothing to protect ahead of.

3. **Confirm JIT is enabled for the Devices location and review current scope/settings.**
   Purview portal > Settings > Data Loss Prevention > Just-in-time protection. *Good:* Devices checkbox selected, scope and fallback action match intended design. *Bad:* not enabled, or scope broader/narrower than intended.

4. **Spot-check Activity Explorer for real JIT events.**
   Filter Activity Explorer for events where `JIT triggered = true`; review the `Enforcement mode` field distribution (Audit vs. Block) against expectations.
   *Good:* event volume and mode distribution match the configured scope and policy set. *Bad:* zero events despite in-scope users performing monitored activities — revisit Validation Steps 1-3.

5. **Confirm exclusion-list correctness (both general and JIT-specific).**
   Cross-reference the JIT-specific app/file-path/file-extension exclusion lists against the general Endpoint DLP "File path exclusions for Windows" setting to confirm which is actually governing a given "why wasn't this excluded" report.

## Troubleshooting Steps (by phase)

**Phase 1 — Prerequisite floor confirmation**
Confirm antimalware client version fleet-wide before investigating any specific incident — this single check resolves a large share of "JIT isn't working" reports.

**Phase 2 — Underlying policy confirmation**
Confirm a genuine Block-capable Endpoint DLP policy exists and targets the activity in question; JIT troubleshooting without this step risks chasing a phantom JIT defect that's actually a policy-authoring gap.

**Phase 3 — Scope and settings review**
Confirm JIT scope, fallback action, and all four fine-tuning settings (clipboard control, app/file-extension/file-path exclusions) match documented intent for the affected user/device.

**Phase 4 — Timing-model validation**
For any specific incident, classify the activity type (resume-capable vs. not) and validate observed behavior against the correct documented timing track (3s/2s/5s/30s) before concluding a defect.

**Phase 5 — Roadmap-562991 interaction check (if applicable)**
If the tenant has the newer JIT Audit user/group scoping capability, treat its interaction with the base JIT scope setting as an open question — document observed behavior precisely and avoid presenting an assumed precedence as documented fact.

**Phase 6 — Escalation**
Package the Evidence Pack and escalate genuine defects (behavior inconsistent with the documented workflow after Phases 1-4 are ruled out) to Microsoft Support.

## Remediation Playbooks

<details><summary>Playbook 1 — Rolling out JIT protection to a new device population</summary>

1. Confirm fleet-wide antimalware client version readiness (Validation Step 1) and remediate any devices below `4.18.23080` before enabling JIT for them.
2. Confirm the target Endpoint DLP policies already have the intended Block/Block-with-override rules configured and tested *without* JIT first, per Microsoft's own best-practice guidance — this avoids unnecessary user-facing blocking during the policy's own tuning period.
3. Enable JIT for Devices with **Fallback action in case of failure = Allow** initially (the documented, cautious default), and a narrow pilot scope.
4. Monitor Activity Explorer JIT events for the pilot population; widen scope incrementally.
5. Only after the pilot is stable, consider enabling **Control copying to clipboard** or moving fallback action to Block — both are explicitly flagged by Microsoft as higher-impact settings warranting deliberate, tested rollout.

**Rollback:** disable JIT for Devices, or narrow scope back to the prior population — changes propagate within the standard up-to-one-hour window.

</details>

<details><summary>Playbook 2 — Diagnosing a reported false-positive JIT block</summary>

1. Confirm the specific activity type and check it against the correct timing track (resume-capable vs. not) in How It Works.
2. Pull the Activity Explorer JIT event for the specific incident — confirm `Enforcement mode` and timestamp alignment with the documented 3s/2s/5s/30s windows.
3. Cross-check whether the destination should have matched an allowed printer/USB/network-share/URL entry, or a JIT-specific app/file-path/file-extension exclusion — remembering the JIT-specific file-path exclusion does **not** exempt the file from ordinary DLP evaluation, only from JIT's own timing-gap enforcement.
4. If the block is explained by a legitimate, intended underlying DLP Block rule (i.e., JIT behaved correctly by acting as a stand-in ahead of a real, intended block), this is not a JIT defect — it's a DLP policy-design conversation with the requesting business unit.

**Rollback:** not applicable — diagnostic playbook only.

</details>

## Evidence Pack

```powershell
<#
.SYNOPSIS
    Read-only evidence collector for Endpoint DLP JIT protection escalations.
.NOTES
    Run the Advanced Hunting portion separately in the Defender/Security portal
    (Investigation & response > Advanced hunting) — this script covers the
    Security & Compliance PowerShell side only.
#>
$OutputPath = "C:\EndpointDLP-JIT-Evidence"
New-Item -ItemType Directory -Path $OutputPath -Force | Out-Null

Get-DlpCompliancePolicy | Where-Object { $_.Workload -match "Endpoint" } |
    Select-Object Name, Enabled, Mode, Workload |
    Export-Csv "$OutputPath\EndpointDlpPolicies.csv" -NoTypeInformation

Get-DlpComplianceRule |
    Select-Object Name, ParentPolicyName, BlockAccess, BlockAccessScope, Disabled |
    Export-Csv "$OutputPath\EndpointDlpRules.csv" -NoTypeInformation

Write-Host "Evidence exported to $OutputPath." -ForegroundColor Yellow
Write-Host "Also manually capture: JIT enabled state + scope + fallback action + fine-tuning" -ForegroundColor Yellow
Write-Host "settings (Purview portal, no cmdlet surface); Activity Explorer JIT event detail;" -ForegroundColor Yellow
Write-Host "and the Advanced Hunting antimalware-client-version query output." -ForegroundColor Yellow
```

## 🎓 Learning Pointers

- JIT protection has **no independent detection logic** — every action it takes is a stand-in for an eventual, already-configured Endpoint DLP Block/Block-with-override verdict. Troubleshooting JIT always starts with confirming that underlying policy exists.
- Two timing tracks exist depending on activity type: **resume-capable** (removable media, network share copy — 3s/2s/5s/30s windows with automatic resume) vs. **non-resume** (print, RDP, Bluetooth, clipboard — user must manually retry). Judging a non-resume activity against resume-capable timing expectations is a common false-defect report.
- JIT's own file-path exclusion setting is **narrower** than the general Endpoint DLP "File path exclusions for Windows" setting — the former only skips JIT's timing-gap enforcement, the latter exempts the path from Endpoint DLP entirely. Conflating the two produces confusing "I excluded it and it's still being evaluated" tickets.
- Clipboard copy is **Audit by default** — escalating it to Block-capable requires explicitly enabling "Control copying to clipboard," which Microsoft flags as a productivity-impacting setting warranting pilot testing.
- The newer **JIT Audit user/group scoping** capability (Roadmap 562991) has no primary Microsoft Learn documentation and a disputed GA date across secondary sources (July vs. September CY2026) — verify its live presence and exact interaction with the pre-existing general JIT scope setting directly in the Purview portal before treating either as settled.
- Primary sources: [Get started with Endpoint DLP Just-in-time protection](https://learn.microsoft.com/en-us/purview/endpoint-dlp-get-started-jit) and [Learn about Endpoint DLP just-in-time protection](https://learn.microsoft.com/en-us/purview/endpoint-dlp-learn-about-jit).
