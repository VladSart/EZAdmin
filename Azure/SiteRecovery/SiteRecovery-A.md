## Scope & Assumptions

This file covers **Azure-to-Azure (A2A) disaster recovery** — replicating
Azure IaaS VMs from one Azure region (or zone) to another using Azure Site
Recovery. It assumes:

- Managed disks are the primary path throughout. Unmanaged (VHD-in-storage-
  account) disk replication is covered only where it materially differs
  (disk replication configuration, target storage account requirements).
- **VMware-to-Azure and Hyper-V-to-Azure (on-premises source) disaster
  recovery are explicitly out of scope.** Both use a materially different
  architecture — a Configuration Server/Process Server (Classic) or a
  Site Recovery replication appliance (Modernized) mediating between an
  on-premises environment and Azure, with agent push-install and
  different failure modes (appliance health, VMM/Hyper-V host connectivity)
  than the pure-Azure A2A scenario this file documents. A dedicated
  on-premises-to-Azure topic is a candidate for a future build.
- **Azure Backup (Recovery Services Vault VM disk backup) is a separate,
  though related, service and is out of scope here** — see
  `Azure/Backup/AzureBackup-A.md`. Both share the vault construct and can
  live in the same Recovery Services vault, but Site Recovery is
  continuous block-level replication with an RPO measured in minutes;
  Azure Backup is scheduled snapshot-based backup with an RPO measured in
  hours/days. A vault showing "healthy" for one tells you nothing about
  the other.
- The VM Agent / extension pipeline (Mobility Service is installed as a
  standard Azure VM extension) is a **separate concern**, documented in
  `Compute/VMExtensions-A.md`. If the extension itself won't provision,
  that's the wrong file to start troubleshooting from.

## How It Works

<details><summary>Full architecture</summary>

### The replication pipeline, end to end

```
┌──────────────────────────────────────────────────────────────┐
│  Recovery Services Vault (control plane)                      │
│  Vault context must be set per PowerShell session before any  │
│  Asr* cmdlet returns meaningful data                           │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  Fabric (one object per Azure region) → Protection Container  │
│  → Protection Container Mapping → Replication Policy          │
│  Created once during setup; a policy defines recovery-point    │
│  retention (hours) and app-consistent snapshot frequency        │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  Mobility Service extension, installed on the source VM        │
│  A standard Azure VM extension — depends on the VM Agent/       │
│  WireServer layer exactly like any other extension              │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  Cache storage account — IN THE SOURCE REGION                  │
│  Every disk write lands here FIRST (block-level, near-          │
│  continuous), before being shipped to the target region         │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  Target region — managed disks (or target storage account       │
│  for unmanaged disks). Recovery points are materialized here.   │
└──────────────────────────────────────────────────────────────┘
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  Replication health (Healthy/Warning/Critical) + RPO             │
│  Computed end-to-end; a break anywhere above degrades this        │
└──────────────────────────────────────────────────────────────┘
```

### Two independent recovery-point tracks

Site Recovery produces two different kinds of recovery point, generated by
two architecturally separate mechanisms:

- **Crash-consistent**, every 5 minutes, always. Block-level replication
  of disk writes — equivalent to what you'd get from pulling the power
  cord at that instant. If this stops for 60 minutes, Error 153007 fires.
- **App-consistent**, on the frequency configured in the replication
  policy (`ApplicationConsistentSnapshotFrequencyInHours`). Uses VSS
  (Windows) or a custom pre/post script (Linux) to quiesce the
  application before the snapshot. If this stops, Error 153006 fires —
  **crash-consistent replication can be completely healthy at the same
  time**, since the two mechanisms don't depend on each other.

This split is the single most useful mental model for triaging "recovery
point" errors: 153007 is a block-level/data-churn/network problem; 153006
is an application/VSS problem on the guest OS, with a well-documented set
of known workload-specific causes (SQL Server version-specific VSS bugs,
Storage Spaces Direct being unsupported for app-consistency entirely, and
Linux requiring an explicit custom script since there's no VSS equivalent).

### Data churn limits: a property of disk size, not performance tier

Site Recovery's supported churn (data change rate) is documented per disk
size, not per performance tier. A 128 GiB Premium SSD (base tier P10) has
a specific churn ceiling; changing that same disk's performance tier to
P50 **without changing its size** does not raise the ceiling — the limit
tracks size. The only two remediations for a disk that's genuinely
exceeding its churn limit are excluding it from replication or increasing
its size (which also, incidentally, changes its tier baseline). High
Churn support (Premium Block Blob cache storage accounts) raises the
ceiling further for workloads that need it — and is mandatory, not
optional, for replicating Premium SSD v2 or Ultra Disk-backed VMs, which
Site Recovery does not support any other way.

### Disk tier/SKU changes and recovery point validity

Whenever a replica disk's tier or SKU changes, Azure's disk resource
provider regenerates the underlying snapshots ("bookmarks") that back
existing recovery points. Recovery points created before that change can
end up referencing bookmarks that no longer exist at the resource
provider. Triggering a failover against one of those stale recovery
points fails with `BookmarkNotFound`. Recovery-point pruning runs on its
own schedule, so a now-unusable recovery point may remain visible in the
portal for a while after the disk change — its continued presence in the
list is not a sign it's still usable.

### Failover and failback: a four-stage state machine

```
Stage 1 — FAILOVER            On-prem/source site down or DR test triggered.
                               Azure VMs are created in the recovery region
                               from the most recent (or a chosen) recovery
                               point. Commit finalizes the failover.

Stage 2 — REPROTECT           The failed-over Azure VM is now UNPROTECTED
(mandatory, not automatic)    until you explicitly reverse replication
                               direction (Update-AzRecoveryServicesAsr-
                               ProtectionDirection). This requires a new
                               cache storage account in what is now the
                               source region (the original recovery region).

Stage 3 — FAILBACK FAILOVER   Once the original region/site is healthy
                               again, a second failover moves the VM back,
                               using the reverse-direction replication
                               established in Stage 2.

Stage 4 — REPROTECT AGAIN     To restore full steady-state DR coverage,
                               replication must be re-established forward
                               (original region → recovery region) again.
```

Skipping Stage 2 is the most common real-world gap: a client's DR test or
genuine failover "succeeds," but nobody reverses replication afterward,
leaving the production workload running unprotected in the recovery
region — sometimes for months — until someone notices during an audit or
the next DR drill.

### Test failover: what "successful" actually means

A test failover creates an isolated copy of the VM (in a network you
explicitly designate — never the production recovery network) without
affecting ongoing replication of the real, protected item. Microsoft's
own guidance is to run one **at least every six months**. Critically, a
test failover is only counted as successful if **both** the failover
itself **and** the subsequent test-failover-cleanup operation complete —
a test that boots successfully but is never cleaned up is not a
completed test in the dashboard's own accounting.

### Capacity Reservation for guaranteed failover capacity

By default, a failover competes for compute capacity in the recovery
region like any other VM deployment — there's no guarantee the exact VM
SKU you need is available at the moment you need it. A Capacity
Reservation, created for the target VM SKU in the recovery region (or
zone) and referenced in the target VM's Compute properties, earmarks that
capacity in advance so Site Recovery doesn't have to compete for it
during an actual disaster.

### Cost model

Site Recovery bills per protected instance, based on the average daily
number of instances protected over a monthly billing period, with the
first 31 days of protection for any given instance free. Underlying
consumed resources — the cache storage account, target region storage/
disks, and network egress during replication — are billed separately
under their own meters, not bundled into the per-instance Site Recovery
charge.

## Dependency Stack

```
▲ Replication health / RPO (computed end-to-end)
│
▼ Target region managed disks / target storage account   (recovery points materialize here)
▼ Cache storage account (SOURCE region)                   (the real network/churn bottleneck)
▼ Mobility Service extension                              (VMExtensions-A.md territory below this)
▼ Fabric / Protection Container / Mapping / Policy         (setup-time objects, rarely the fault)
▼ Recovery Services Vault (control plane, per-session context)
```

Diagnosis works top-down from the observed symptom (a specific error ID or
health state) but the actual fault is usually in the middle of the stack —
the cache storage account or Mobility Service layers — not at either end.

## Symptom → Cause Map

| Symptom | Most Likely Cause | Check |
|---|---|---|
| `ReplicationHealth` = `Critical`, Error 153007 | Data churn exceeds the disk's size-based limit, or a network path problem to the cache storage account | Portal Events (last 72h) for "Data change rate beyond supported limits"; `AzCopy` throughput test |
| `ReplicationHealth` = `Critical`, Error 153006 | App-consistent (VSS) failure — crash-consistent replication may still be fully healthy | `vacp.log` on the source VM; known SQL Server/S2D/Linux-script causes |
| Failover fails with `BookmarkNotFound` | Recovery point predates a disk tier/SKU change; the referenced snapshot no longer exists | Compare recovery point timestamp against disk `TimeCreated`/resize history |
| No replication health data returned by any `Asr*` cmdlet | Vault context not set for this session | `Set-AzRecoveryServicesAsrVaultContext` |
| RPO climbing but health still shows `Normal` | RPO alerting threshold is separate from health-state computation | Don't wait for a health-state change before investigating a rising RPO trend |
| `ProvisioningState` on the Mobility Service extension isn't `Succeeded` | This is a VM Agent/extension-pipeline problem, not an ASR-specific one | Cross-check `Compute/VMExtensions-B.md` before troubleshooting ASR symptoms |
| Configuration Issues panel still shows a fixed issue | The validator runs every 12 hours by default; the dashboard is stale until the next pass | Force a refresh via the portal's Configuration Issues refresh icon |
| VM fails over successfully but is unprotected afterward | Stage 2 (Reprotect) was never run — this does not happen automatically | `Update-AzRecoveryServicesAsrProtectionDirection` |
| Failed to create the encrypted/high-churn cache storage account | High Churn requires a Premium Block Blob (`SkuName Premium_LRS`, `Kind BlockBlobStorage`) storage account specifically — a Standard account can't be upgraded in place for this purpose | Recreate the cache storage account with the correct SKU/Kind before retrying replication enablement |
| Replicating a Premium SSD v2 or Ultra Disk-backed VM fails to enable | These disk types are only supported under Site Recovery via High Churn — there is no non-High-Churn path for them | Confirm the cache storage account is Premium Block Blob before troubleshooting further |
| Test failover "succeeded" but the dashboard still shows "Test recommended" | Test-failover-cleanup was never run — a boot without cleanup doesn't count as a completed test | Run `Start-AzRecoveryServicesAsrTestFailoverCleanupJob` |
| Reprotection (`Update-AzRecoveryServicesAsrProtectionDirection`) fails citing a missing cache storage account | The now-source region (previously the recovery region) needs its OWN new cache storage account — the original one doesn't carry over | Create a cache storage account in the current source region before retrying |
| VSS-related failure only on one specific SQL Server-hosting VM | A documented per-version SQL Server VSS interaction, not a general Site Recovery defect | Match the exact SQL Server version/build against the known-issue list before assuming a config error |
| Mobility Service shows no heartbeat despite the VM and service being up | Local `RCMInfo.conf` references an expired/rotated AAD tenant or client ID | Retrieve current IDs via the protected item's own GET API response, update the conf file, restart agent services |

## Validation Steps

**1. Vault context is actually set for this session**
```powershell
Set-AzRecoveryServicesAsrVaultContext -Vault (Get-AzRecoveryServicesVault -ResourceGroupName "<vaultRg>" -Name "<vaultName>")
Get-AzRecoveryServicesAsrFabric | Select-Object Name, FabricType
```
Good: fabric objects return without error. Bad: an authentication or "not found" error — resolve vault access before anything else.

**2. Replication health and protection state, fleet-wide**
```powershell
Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $container |
  Select-Object FriendlyName, ProtectionState, ReplicationHealth
```
Good: `Protected` / `Normal` (or `Healthy`, portal terminology varies slightly from cmdlet output) for every steady-state item. Bad: any `Critical`, or a `ProtectionState` you don't expect for that item's current lifecycle stage.

**3. RPO against the configured policy retention**
```powershell
$rpi.ProviderSpecificDetails.RPOInSeconds
```
Good: a value comfortably within your recovery-point retention window. Bad: an RPO climbing steadily over multiple checks — this precedes a health-state flip to Critical, don't wait for the flip to investigate.

**4. Recovery point availability and type**
```powershell
Get-AzRecoveryServicesAsrRecoveryPoint -ReplicationProtectedItem $rpi | Sort-Object RecoveryPointTime -Descending | Select-Object -First 5
```
Good: a recent, healthy mix of `CrashConsistent` and `AppConsistent` points. Bad: only crash-consistent points appearing (app-consistency is failing silently until you check), or the newest point predating a disk change you're about to fail over against.

**5. Cache storage account reachability and throughput**
```powershell
azcopy bench "https://<cacheStorageAccount>.blob.core.windows.net/<container>?<sasToken>" --mode=Upload
```
Good: throughput comfortably above the ~4 MB/3 sec baseline. Bad: sustained low throughput — check for an NVA in the outbound path before assuming a bandwidth shortage.

**6. Configuration issues are current, not stale**
```powershell
Get-AzRecoveryServicesAsrJob | Where-Object DisplayName -like "*Validat*" | Sort-Object StartTime -Descending | Select-Object -First 1
```
Good: a validation job timestamp newer than your last configuration fix. Bad: the most recent validation predates your fix — force a refresh before trusting the dashboard.

**7. Test failover recency and full completion**
```powershell
Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $container |
  Select-Object FriendlyName, @{N='LastTestFailover';E={$_.ProviderSpecificDetails.LastTestFailoverStatus}}
```
Good: a completed test (failover + cleanup) within 6 months. Bad: "Test recommended" status, or a test failover that was run but never cleaned up.

## Troubleshooting Steps (by phase)

**Phase 1 — Classify the health state and error ID before acting.** Pull
`ReplicationHealth` and the specific error ID from the portal's Errors tab
(or job history). Don't start remediating from a vague "replication is
broken" — 153007 and 153006 point at entirely different layers of the
stack and have zero remediation overlap.

**Phase 2 — Isolate which recovery-point track is affected.** Crash-
consistent failing (153007) is a block-level/churn/network problem.
App-consistent failing (153006) is a guest-OS VSS/workload problem. A
health-Critical item with BOTH failing usually means the underlying
churn/network problem is severe enough to also be starving the VSS
snapshot window — fix the crash-consistent path first in that case.

**Phase 3 — Confirm the extension layer is healthy before assuming an
ASR-specific fault.** The Mobility Service is a standard VM extension. If
its `ProvisioningState` isn't `Succeeded`, hand this off to
`Compute/VMExtensions-B.md` first — there's no point troubleshooting
churn limits on an extension that isn't even running.

**Phase 4 — For failover-time errors, check disk history before
retrying blindly.** A `BookmarkNotFound` error means the chosen recovery
point is stale relative to a disk tier/SKU change — the fix is picking a
different recovery point, not retrying the same one.

**Phase 5 — After any failover, verify Stage 2 (Reprotect) actually
happened.** This is a process/checklist failure far more often than a
technical one — confirm reprotection status explicitly rather than
assuming "the failover succeeded" implies ongoing protection.

## Remediation Playbooks

<details><summary>Playbook 1 — Full A2A replication setup from PowerShell (reference sequence)</summary>

**When to use:** Onboarding a new client VM to Site Recovery, or rebuilding
protection after a Disable Replication / disaster recovery drill reset.

```powershell
# 1. Vault + vault context
$vault = New-AzRecoveryServicesVault -Name "<vaultName>" -ResourceGroupName "<vaultRg>" -Location "<recoveryRegion>"
Set-AzRecoveryServicesAsrVaultContext -Vault $vault

# 2. Fabrics (one per region) + protection containers + replication policy + container mapping
$primaryFabric  = New-AzRecoveryServicesAsrFabric -Azure -Location "<sourceRegion>" -Name "<sourceFabricName>"
$recoveryFabric = New-AzRecoveryServicesAsrFabric -Azure -Location "<recoveryRegion>" -Name "<recoveryFabricName>"
$primaryContainer  = New-AzRecoveryServicesAsrProtectionContainer -InputObject $primaryFabric -Name "<sourceContainer>"
$recoveryContainer = New-AzRecoveryServicesAsrProtectionContainer -InputObject $recoveryFabric -Name "<recoveryContainer>"
$policy = New-AzRecoveryServicesAsrPolicy -AzureToAzure -Name "<policyName>" -RecoveryPointRetentionInHours 24 -ApplicationConsistentSnapshotFrequencyInHours 4
$mapping = New-AzRecoveryServicesAsrProtectionContainerMapping -Name "<mappingName>" -Policy $policy -PrimaryProtectionContainer $primaryContainer -RecoveryProtectionContainer $recoveryContainer

# 3. Cache storage account (SOURCE region — standard, or Premium Block Blob for High Churn)
$cacheSA = New-AzStorageAccount -Name "<cacheAccountName>" -ResourceGroupName "<sourceRg>" -Location "<sourceRegion>" -SkuName Standard_LRS -Kind Storage

# 4. Network mapping (source VNet -> recovery VNet)
New-AzRecoveryServicesAsrNetworkMapping -AzureToAzure -Name "<netMappingName>" -PrimaryFabric $primaryFabric -PrimaryAzureNetworkId "<sourceVNetId>" -RecoveryFabric $recoveryFabric -RecoveryAzureNetworkId "<recoveryVNetId>"

# 5. Enable replication (managed disks) — one disk replication config object per disk
$vm = Get-AzVM -ResourceGroupName "<rg>" -Name "<vmName>"
$osDiskConfig = New-AzRecoveryServicesAsrAzureToAzureDiskReplicationConfig -ManagedDisk -LogStorageAccountId $cacheSA.Id `
  -DiskId $vm.StorageProfile.OsDisk.ManagedDisk.Id -RecoveryResourceGroupId "<recoveryRgId>" `
  -RecoveryReplicaDiskAccountType $vm.StorageProfile.OsDisk.ManagedDisk.StorageAccountType `
  -RecoveryTargetDiskAccountType $vm.StorageProfile.OsDisk.ManagedDisk.StorageAccountType

New-AzRecoveryServicesAsrReplicationProtectedItem -AzureToAzure -AzureVmId $vm.Id -Name (New-Guid).Guid `
  -ProtectionContainerMapping $mapping -AzureToAzureDiskReplicationConfiguration @($osDiskConfig) -RecoveryResourceGroupId "<recoveryRgId>"
```

**Rollback:** Nothing here is destructive to the source VM — replication
is additive. If setup fails partway through, `Remove-AzRecoveryServicesAsrReplicationProtectedItem`
cleanly tears down the protected item without touching the source VM.

</details>

<details><summary>Playbook 2 — Test failover, validate, and clean up</summary>

```powershell
# Isolated test network — never the production recovery network
$tfoVnet = New-AzVirtualNetwork -Name "<tfoVnetName>" -ResourceGroupName "<recoveryRg>" -Location "<recoveryRegion>" -AddressPrefix "10.99.0.0/16"

$rpi = Get-AzRecoveryServicesAsrReplicationProtectedItem -FriendlyName "<vmName>" -ProtectionContainer $primaryContainer
$tfoJob = Start-AzRecoveryServicesAsrTestFailoverJob -ReplicationProtectedItem $rpi -AzureVMNetworkId $tfoVnet.Id -Direction PrimaryToRecovery

# Wait, then validate the test VM manually (RDP/SSH, application checks)

# MANDATORY — a test isn't "complete" in the dashboard's accounting without this:
Start-AzRecoveryServicesAsrTestFailoverCleanupJob -ReplicationProtectedItem $rpi
```

**Rollback:** The cleanup job IS the rollback — it deletes the test copy
and leaves ongoing replication of the real protected item completely
untouched throughout.

</details>

<details><summary>Playbook 3 — Full failover, commit, then reprotect (Stages 1-2)</summary>

```powershell
# Stage 1 — Failover
$recoveryPoints = Get-AzRecoveryServicesAsrRecoveryPoint -ReplicationProtectedItem $rpi | Sort-Object RecoveryPointTime -Descending
$failoverJob = Start-AzRecoveryServicesAsrUnplannedFailoverJob -ReplicationProtectedItem $rpi -Direction PrimaryToRecovery -RecoveryPoint $recoveryPoints[0]
# poll Get-AzRecoveryServicesAsrJob until State -eq "Succeeded"
Start-AzRecoveryServicesAsrCommitFailoverJob -ReplicationProtectedItem $rpi

# Stage 2 — Reprotect (MANDATORY — do not skip). New cache storage account in the now-source region:
$reverseCacheSA = New-AzStorageAccount -Name "<reverseCacheName>" -ResourceGroupName "<originalSourceRg>" -Location "<originalSourceRegion>" -SkuName Standard_LRS -Kind Storage
Update-AzRecoveryServicesAsrProtectionDirection -ReplicationProtectedItem $rpi -AzureToAzure `
  -ProtectionContainerMapping $reverseMapping -LogStorageAccountId $reverseCacheSA.Id -RecoveryResourceGroupID "<originalSourceRgId>"
```

**Rollback:** Failover creates a new Azure VM from replicated data — it
does not delete or modify the original source VM/disks. If a failover
needs to be abandoned, the original resources are still intact to resume
from; only the newly-created failed-over VM needs cleanup.

</details>

<details><summary>Playbook 4 — Data churn remediation (disk exclusion or resize)</summary>

```powershell
# Confirm which disk is the actual offender via portal Events, then either:

# Exclude the disk (requires a brief replication disable/re-enable cycle)
Remove-AzRecoveryServicesAsrReplicationProtectedItem -ReplicationProtectedItem $rpi
# Re-enable replication with a disk config list that OMITS the offending disk's DiskId

# OR resize the replica disk in the target region (raises the size-based churn ceiling)
$replicaDisk = Get-AzDisk -ResourceGroupName "<recoveryRg>" -DiskName "<replicaDiskName>"
$replicaDisk.DiskSizeGB = 512
Update-AzDisk -ResourceGroupName "<recoveryRg>" -DiskName "<replicaDiskName>" -Disk $replicaDisk
```

**Rollback:** Disk exclusion is reversible by re-adding the disk to the
replication configuration later. A disk size increase is not reversible
without shrinking (which Azure Disks generally don't support in place) —
size conservatively against actually-observed churn, not a guess.

</details>

## Evidence Pack

```powershell
<#
.SYNOPSIS    Collects Azure Site Recovery (A2A) diagnostic evidence for escalation.
.DESCRIPTION Read-only. Gathers replication health, RPO, recovery point recency, and
             recent job failures for a single protected item, then writes a summary
             object suitable for pasting into a support ticket. Does not modify
             replication state or trigger any failover/reprotect action.
.PARAMETER   VaultResourceGroupName  Resource group containing the Recovery Services vault.
.PARAMETER   VaultName               Name of the Recovery Services vault.
.PARAMETER   VMFriendlyName          Friendly name of the protected item (source VM name).
.EXAMPLE     .\Get-SiteRecoveryEvidence.ps1 -VaultResourceGroupName rg-dr -VaultName vault-dr -VMFriendlyName vm-web01
.NOTES       Requires an authenticated Az PowerShell session (Connect-AzAccount).
             Read-only — see Azure/SiteRecovery/Scripts/Get-SiteRecoveryHealth.ps1 for the
             full, parameterized, fleet-capable version of this script.
#>
param(
    [Parameter(Mandatory)][string]$VaultResourceGroupName,
    [Parameter(Mandatory)][string]$VaultName,
    [Parameter(Mandatory)][string]$VMFriendlyName
)

$vault = Get-AzRecoveryServicesVault -ResourceGroupName $VaultResourceGroupName -Name $VaultName
Set-AzRecoveryServicesAsrVaultContext -Vault $vault

$fabrics = Get-AzRecoveryServicesAsrFabric
$rpi = $null
foreach ($fabric in $fabrics) {
    $containers = Get-AzRecoveryServicesAsrProtectionContainer -Fabric $fabric
    foreach ($c in $containers) {
        $found = Get-AzRecoveryServicesAsrReplicationProtectedItem -ProtectionContainer $c -ErrorAction SilentlyContinue |
            Where-Object FriendlyName -eq $VMFriendlyName
        if ($found) { $rpi = $found }
    }
}

if (-not $rpi) { throw "No protected item found with friendly name '$VMFriendlyName'." }

$recentPoints = Get-AzRecoveryServicesAsrRecoveryPoint -ReplicationProtectedItem $rpi -ErrorAction SilentlyContinue |
    Sort-Object RecoveryPointTime -Descending | Select-Object -First 5
$recentFailedJobs = Get-AzRecoveryServicesAsrJob -ErrorAction SilentlyContinue |
    Where-Object { $_.State -eq "Failed" -and $_.TargetObjectName -eq $VMFriendlyName -and $_.StartTime -gt (Get-Date).AddDays(-3) }

[PSCustomObject]@{
    VMFriendlyName       = $VMFriendlyName
    ProtectionState      = $rpi.ProtectionState
    ReplicationHealth    = $rpi.ReplicationHealth
    RPOInSeconds          = $rpi.ProviderSpecificDetails.RPOInSeconds
    LastTestFailoverStatus = $rpi.ProviderSpecificDetails.LastTestFailoverStatus
    MostRecentRecoveryPoints = ($recentPoints | ForEach-Object { "$($_.RecoveryPointType) @ $($_.RecoveryPointTime)" }) -join '; '
    RecentFailedJobs3Days = ($recentFailedJobs | ForEach-Object { "$($_.DisplayName) [$($_.StartTime)]: $($_.StateDescription)" }) -join '; '
} | Format-List
```

## 🎓 Learning Pointers

- **Crash-consistent and app-consistent recovery points are architecturally independent tracks.** Understanding this split (153007 vs. 153006) is the single fastest way to correctly scope a "recovery point" ticket before touching anything.
- **Churn limits scale with disk size, not performance tier** — a client who "already upgraded to a faster tier" and still sees churn errors needs a size increase, not a further tier upgrade, and Premium SSD v2/Ultra Disk VMs require High Churn (Premium Block Blob cache storage) with no non-High-Churn alternative.
- **The cache storage account is in the source region and is the real data-plane bottleneck for most network/latency tickets** — checking firewall/NSG rules in the vault's or target region first is a common, easily-avoided time sink.
- **A disk tier/SKU change silently invalidates older recovery points via bookmark regeneration** — `BookmarkNotFound` at failover time is almost always this, not a genuine replication defect, and the fix is picking a newer recovery point.
- **Reprotection after a failover is a manual, mandatory step, not an automatic consequence of a successful failover.** This is the single most common real-world gap this repo has seen across DR-related topics — a "successful" failover with no reprotection leaves a client's production workload unprotected indefinitely.
- **A test failover only counts as complete once both the failover AND its cleanup job succeed** — a client who says "we tested DR" but never ran cleanup hasn't completed Microsoft's own definition of a successful test.
