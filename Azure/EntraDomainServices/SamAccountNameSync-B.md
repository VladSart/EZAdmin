## ⚠ Scope note — this is a different setting from ordinary sAMAccountName autogeneration

`EntraDomainServices-B.md` Fix 3 already covers the *existing*, always-on behavior: sAMAccountName is autogenerated from `mailNickname` or the UPN prefix, with truncation/de-duplication, and sign-in intermittently fails when a user expects a different value. **This runbook covers a separate, opt-in Public Preview feature** (Microsoft Learn, `security-account-name`, ms.date 2026-08-18, last updated 2026-08-24): **enhanced sAMAccountName synchronization**, which changes the *source* of sAMAccountName for hybrid users from the old autogeneration logic to the `onPremisesSamAccountName` attribute already present in Microsoft Entra ID. If the ticket is about a sign-in failure or unexpected value on a managed domain that has **not** had this preview feature touched, go to `EntraDomainServices-B.md` instead.

## Triage

```powershell
# 1. Confirm this feature applies at all — Enterprise/Premium SKU only
Get-AzADDomainService -Name "<domainServiceName>" -ResourceGroupName "<rg>" |
    Select-Object Name, Sku
# Standard SKU: this feature is not available. Stop here — not the cause of the ticket.

# 2. Check whether enhanced sync is enabled for this managed domain
#    (surfaced in the Entra admin center under the managed domain's "Security settings" —
#    no confirmed PowerShell/Graph cmdlet exposes this specific setting as of this preview;
#    verify in-portal, or ask whoever administers Domain Services for this tenant)

# 3. For an affected user, compare Entra ID's source attribute against what
#    Entra Domain Services is currently showing
Get-MgUser -UserId "<upn>" -Property OnPremisesSamAccountName,OnPremisesSyncEnabled |
    Select-Object DisplayName, OnPremisesSamAccountName, OnPremisesSyncEnabled

# 4. Compare against the sAMAccountName actually visible on the managed domain
#    (requires console/RDP access to a management VM domain-joined to the managed domain)
Get-ADUser -Identity "<upn-or-old-samaccountname>" -Server "<managedDomainFQDN>" -Properties SamAccountName |
    Select-Object SamAccountName
```

| Result | Interpretation | Action |
|--------|---------------|--------|
| SKU is Standard | Feature not available — this is not what's causing the ticket | Escalate license upgrade conversation if the client wants this feature |
| `OnPremisesSamAccountName` is empty/null for a hybrid user | Enhanced sync will fall through to the old mailNickname-based generation for this user even if the setting is enabled | → Fix 1 |
| Enhanced sync just got enabled and users report a CHANGED logon name | Expected behavior — enabling this on an **existing** managed domain updates existing hybrid users' sAMAccountName during the next sync | → Fix 2 |
| Managed domain is newly created and behavior is unclear/inconsistent | Microsoft's own documentation for this preview feature contains an internal inconsistency about the default state for new domains — do not assume either way | → Fix 3 |
| Admin trying to change the setting gets denied/can't find the toggle | RBAC gate — requires BOTH Application Administrator AND Groups Administrator, not either alone | → Fix 4 |

## Dependency Cascade

<details><summary>What must be true, and what breaks if you flip this without checking first</summary>

```
Microsoft Entra ID
    └── onPremisesSamAccountName attribute (populated via Microsoft Entra Connect
          Sync/Cloud Sync from on-prem AD DS — this is a READ of an existing
          hybrid-sync attribute, not a new sync pipeline)
          │
          ▼
Microsoft Entra Domain Services managed domain — "sAMAccountName synchronization
from on-premises" setting (Security settings blade)
    │
    ├── Setting DISABLED (default on existing managed domains)
    │     └── sAMAccountName generated from mailNickname / UPN prefix,
    │           with truncation (20-char legacy limit) and de-duplication
    │
    └── Setting ENABLED
          ├── Hybrid users -> sAMAccountName sourced from onPremisesSamAccountName
          │     └── EXISTING hybrid users are UPDATED during the next sync —
          │           this is a live rename of a legacy logon identifier on
          │           accounts that may already be in production use
          │                 ├── Scripts/scheduled tasks hardcoding the OLD
          │                 │     generated sAMAccountName -> break silently
          │                 ├── Legacy LDAP-bind apps keyed on sAMAccountName -> break
          │                 └── DOMAIN\username logon habit -> changes for affected users
          └── Cloud-only users (no onPremisesSamAccountName) -> UNAFFECTED,
                always continue mailNickname-based generation regardless of setting
```

</details>

## Diagnosis & Validation Flow

**1. Confirm SKU eligibility first — this is a hard, silent gate**
```powershell
Get-AzADDomainService -Name "<domainServiceName>" -ResourceGroupName "<rg>" | Select-Object Sku
```
Expected: `Enterprise` or `Premium`. On `Standard`, the feature is documented as unavailable — Microsoft's page does not specify the exact UI error shown, so don't assume a specific error string; confirm directly in the Entra admin center Security settings blade for that managed domain.

**2. Confirm the admin attempting the change holds BOTH required roles**
```powershell
Get-MgUserMemberOf -UserId "<adminUpn>" | Select-Object -ExpandProperty AdditionalProperties |
    Where-Object { $_.displayName -in @("Application Administrator","Groups Administrator") }
```
Expected: both role names present. Microsoft's documentation does not explain why Groups Administrator is required for what is otherwise an attribute-sync/authentication setting — treat this as a documented requirement to satisfy, not a misconfiguration to "fix."

**3. Confirm the source attribute is populated before enabling, for every affected hybrid user**
```powershell
Get-MgUser -All -Filter "onPremisesSyncEnabled eq true" -Property DisplayName,UserPrincipalName,OnPremisesSamAccountName |
    Where-Object { -not $_.OnPremisesSamAccountName } |
    Select-Object DisplayName, UserPrincipalName
```
Expected: an empty result. Any hybrid user returned here will silently keep the OLD mailNickname-based sAMAccountName even after enabling enhanced sync — not itself an error, but a gap worth explaining to the client before they assume "everyone" got the new consistent naming.

**4. After enabling, validate against a small, known sample before declaring done**
```powershell
# Pick 3-5 hybrid users whose onPremisesSamAccountName you already know, then:
Get-ADUser -Identity "<upn>" -Server "<managedDomainFQDN>" -Properties SamAccountName |
    Select-Object SamAccountName
# Compare 1:1 against Get-MgUser's OnPremisesSamAccountName for the same users.
```
Expected: exact match. Then have those same users (or a test account matching their profile) actually authenticate against the managed domain before declaring the change complete — a matching attribute value is necessary but not sufficient proof that dependent apps still work.

## Common Fix Paths

<details><summary>Fix 1 — Hybrid user has no onPremisesSamAccountName, so enhanced sync doesn't apply to them</summary>

```powershell
# This is a Microsoft Entra Connect / Cloud Sync attribute-population issue, not an
# Entra Domain Services issue. Confirm the on-prem AD DS user's own sAMAccountName is
# what you expect, then confirm it's flowing through the sync engine:
Get-ADUser -Identity "<onprem-username>" -Properties SamAccountName   # on-prem AD DS side

# If Entra Connect / Cloud Sync is in use, verify the attribute mapping for
# onPremisesSamAccountName is not excluded by a custom sync rule -- see
# EntraID/Troubleshooting/Connect-Sync-A.md or EntraID/Troubleshooting/CloudSync-A.md
# for the sync-engine side of this, this runbook does not own that layer.
```
**Rollback:** N/A — this is a diagnostic finding, not a configuration change.

</details>

<details><summary>Fix 2 — Expected behavior: enabling on an existing managed domain renamed existing users' logon name</summary>

```powershell
# Confirm this is the expected one-time transition, not an ongoing/repeating problem:
Get-ADUser -Identity "<upn>" -Server "<managedDomainFQDN>" -Properties SamAccountName,whenChanged |
    Select-Object SamAccountName, whenChanged
# whenChanged should align with when the setting was enabled / the next sync cycle after.

# Communicate the new logon name to affected users and update any documentation,
# mapped-drive scripts, or legacy app configuration that referenced the OLD value.
# There is no per-user opt-out once the tenant-wide setting is enabled for hybrid users.
```
**Rollback:** Disabling the setting again is documented as reversible for the TOGGLE itself, but Microsoft's page does not state whether disabling reverts already-renamed users back to their prior generated sAMAccountName, or leaves them on the onPremisesSamAccountName value going forward. **Do not assume either behavior** — test in a non-production managed domain first, or open a support case to confirm before promising a client a clean rollback.

</details>

<details><summary>Fix 3 — New managed domain, unclear/inconsistent default-state behavior</summary>

```powershell
# Microsoft's own "security-account-name" documentation page contains two sections
# with CONTRADICTORY claims about new managed domains:
#   - One section states the setting "will need to be enabled, by default it is disabled"
#   - Another states "enhanced synchronization is enabled by default... this behavior
#     can't be changed" for new domain deployments
# Do not silently pick one. For a new managed domain:
Get-ADUser -Identity "<known-hybrid-upn>" -Server "<managedDomainFQDN>" -Properties SamAccountName
# Compare directly against that user's OnPremisesSamAccountName in Entra ID to determine
# empirically which behavior this tenant/domain actually exhibits, rather than trusting
# either doc section. Log the finding for the client record.
```
**Rollback:** N/A — this is an empirical verification step, not a change.

</details>

<details><summary>Fix 4 — Admin can't find or use the "sAMAccountName synchronization from on-premises" toggle</summary>

```powershell
# Confirm and, if authorized, grant BOTH required roles -- Application Administrator
# is not sufficient alone, and neither is Groups Administrator alone.
Get-MgRoleManagementDirectoryRoleAssignment -Filter "principalId eq '<adminObjectId>'" |
    ForEach-Object { (Get-MgRoleManagementDirectoryRoleDefinition -UnifiedRoleDefinitionId $_.RoleDefinitionId).DisplayName }

# Grant via PIM eligible activation or standing assignment per your tenant's standard
# least-privilege process -- do not grant Groups Administrator broadly just to unblock
# this one setting change; scope/time-box it if using PIM.
```
**Rollback:** remove the added role assignment once the setting change is complete, if it was granted specifically for this task.

</details>

## 🎓 Learning Pointers

- **A config toggle that looks cosmetic can be a live identity-rename operation.** Enabling this setting on an existing managed domain doesn't just change future behavior — it updates the sAMAccountName of every already-provisioned hybrid user during the next sync. Always read "Before you enable the setting" sections on preview features literally; Microsoft's own docs here explicitly warn to review dependent apps/scripts first, and that warning is not boilerplate in this case. [MS Docs: SAM Account Name - Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/identity/domain-services/security-account-name)

- **Primary-source documentation can itself be internally inconsistent — verify empirically rather than pick a section to trust.** This preview's own Learn page states two different defaults for new managed domains in two different sections. Rather than silently choosing the more official-sounding one, this runbook's Fix 3 tells you to check the actual live behavior on the specific managed domain in front of you.

- **A two-role RBAC requirement (Application Administrator AND Groups Administrator) with no stated rationale is still worth documenting as-is.** Not every access-control requirement in Microsoft's platform comes with an explanation — resist the urge to assume it's a documentation error and grant only one role; test with both present.

- **"Preview" means the support and rollback story may be thinner than for GA features.** This runbook's Fix 2 rollback note is deliberately non-committal about whether disabling the setting reverts already-changed sAMAccountName values, because Microsoft's own documentation doesn't say — that gap is itself useful information to set client expectations with before enabling on a production managed domain. [MS Docs: What's new in Microsoft Entra: September 2026](https://techcommunity.microsoft.com/blog/microsoft-entra-blog/what%E2%80%99s-new-in-microsoft-entra-september-2026/4545179)
