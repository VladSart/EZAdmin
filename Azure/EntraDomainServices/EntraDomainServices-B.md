## Triage

Run these from a **management VM domain-joined to the managed domain** (Az PowerShell for the first two, ADAC/AD PowerShell via RSAT for the rest):

```powershell
# 1. Managed domain health — the single most useful first check
Get-AzADDomainService -Name "<managedDomainName>" -ResourceGroupName "<rg>" |
  Select-Object DomainName, DomainSecuritySettings, ReplicaSets, ResourceForestSettings

# 2. Active health alerts on the managed domain (portal: Entra ID > Domain Services > Health)
Get-AzADDomainServiceOutboundNetworkDependency -DomainServiceName "<managedDomainName>" -ResourceGroupName "<rg>"

# 3. Is the affected account even sync-eligible? (run against Microsoft Graph / Entra ID)
Get-MgUser -UserId "<user@tenant.onmicrosoft.com>" -Property UserType,OnPremisesSyncEnabled,AccountEnabled

# 4. From the management VM, confirm the account exists and its lock/enabled state INSIDE the managed domain
#    (do NOT trust Entra ID's view of lockout state — lockout is local to the managed domain only)
Get-ADUser -Identity "<sAMAccountName>" -Server "<managedDomainFQDN>" -Properties LockedOut,Enabled,PasswordLastSet,BadLogonCount

# 5. Confirm the NSG on the managed domain's subnet still matches the platform-managed baseline
Get-AzNetworkSecurityGroup -Name "<managedDomainNsgName>" -ResourceGroupName "<rg>" |
  Select-Object -ExpandProperty SecurityRules
```

| What you see | What it means |
|---|---|
| `Get-AzADDomainService` shows a non-`Running` provisioning/deployment state | Managed domain itself is degraded — check the Health blade for active alerts before troubleshooting individual sign-ins; go to Fix 5 |
| User exists in Entra ID but `Get-ADUser` against the managed domain returns nothing | Sync hasn't caught up yet, the user has never changed their password (cloud-only), or the account is an external/guest account that can never sync — go to Fix 1 |
| `Get-ADUser` shows `LockedOut: True` | Local-to-managed-domain lockout (5 bad attempts / 2 min → 30 min lockout) — this does **not** reflect or affect the account's Entra ID lockout state — go to Fix 2 |
| Sign-in works with `SAMAccountName\user` format intermittently but fails for some users | `SAMAccountName` was autogenerated (mailNickname collision or >20-char UPN prefix) and doesn't match what the user expects — always use UPN format instead — go to Fix 3 |
| NSG on the managed domain's subnet has custom rules beyond the platform baseline, or is missing `AllowVnetInBound`/`AllowAzureLoadBalancerInBound` | Someone edited the auto-created NSG — this is explicitly unsupported and breaks sync/patching/management, not just one user's sign-in — go to Fix 4 |
| A user was recently restored from the Entra ID recycle bin and now can't access resources they used to | Restored users get a **new** GUID/SID in the managed domain — any ACLs on managed-domain resources referencing the old SID are now broken and must be re-applied — go to Fix 6 |
| Enabling Domain Services itself fails with a named-application error | Stale `Microsoft Entra Domain Services Sync` app or `AzureActiveDirectoryDomainControllerServices` app registration from a prior failed/deleted attempt — go to Fix 7 |

## Dependency Cascade

<details><summary>What must be true</summary>

```
Microsoft Entra ID tenant (source of authority — users/groups/credentials)
  │
  ├── Password hash synchronization must be enabled tenant-wide
  │     └── Federated tenants WITHOUT PHS enabled cannot use Domain Services at all
  │           (no password hashes ever land in Entra ID to synchronize onward)
  │
  ├── (Hybrid only) On-prem AD DS → Microsoft Entra Connect → Entra ID
  │     └── Legacy NTLM/Kerberos-compatible hashes must be in scope of Connect's sync
  │
  ▼
One-way background sync: Entra ID → managed domain (automatic, no reverse sync, ever)
  │   Cloud-only users: hash only generated after the user CHANGES their password
  │   post-Domain-Services-enablement — a brand-new cloud user is invisible to the
  │   managed domain until that password change happens
  │
  ▼
Managed domain (2 Microsoft-managed DCs in a replica set)
  │
  ├── Dedicated /27 (or larger) subnet — ONLY managed-domain platform resources here,
  │     never your own VMs/apps
  │         └── Platform-created NSG — editing/deleting its rules breaks sync + management
  │         └── Platform-created LB + public IP + NAT rules — never touch manually
  │
  ├── Flat OU structure — AADDC Users / AADDC Computers; on-prem OU hierarchy is
  │     NOT preserved (custom OUs you create yourself are the exception)
  │
  ▼
Application / VM domain-joined to the managed domain
  └── Authenticates via NTLM/Kerberos/LDAP using SYNCED credentials —
        account lockout state, password expiry (90-day default, independent of
        Entra ID's own policy) are evaluated LOCALLY in the managed domain
```

Key failure points:
- PHS-off federated tenants are a hard blocker, not a misconfiguration to fix — Domain Services simply cannot function without it
- A cloud-only user who has never changed their password since Domain Services was enabled has **no** hash to sync — this is the single most common "new hire can't domain-join their VM" ticket
- Guest/B2B/external accounts never sync credentials — no fix exists short of converting them to a native member account
- Restored (recycle-bin) users get a **new** SID in the managed domain — `SidHistory` only ever carries the *original on-prem* SID forward, never re-derives after a delete/restore cycle

</details>

## Diagnosis & Validation Flow

**Step 1 — Confirm the managed domain itself is healthy before chasing a single user**
```powershell
Get-AzADDomainService -Name "<managedDomainName>" -ResourceGroupName "<rg>"
```
Expected: `Running`/healthy state, no active alerts on the Health blade in the Entra admin center. If the domain itself is degraded, every downstream symptom is noise until this is fixed.

**Step 2 — Confirm the tenant's PHS/federation posture**
```powershell
Get-MgOrganization | Select-Object -ExpandProperty OnPremisesSyncEnabled
# For federated tenants, check whether Password Hash Sync is also enabled as a backup method
# (Entra Connect: Optional Features > Password Hash Synchronization)
```
Expected: PHS enabled tenant-wide (or tenant is cloud-only, which has PHS implicitly). A federated tenant with PHS off cannot authenticate anyone against the managed domain — this is a project-level blocker, not a per-user fix.

**Step 3 — Confirm the specific user's sync eligibility and state in Entra ID**
```powershell
Get-MgUser -UserId "<upn>" -Property UserType,OnPremisesSyncEnabled,AccountEnabled,UserPrincipalName
```
Expected: `UserType: Member` (not `Guest`), `AccountEnabled: True`. A `Guest` UserType explains a sign-in failure completely — stop here, there is no fix, only a workaround (create a native member account).

**Step 4 — Confirm the user object actually landed in the managed domain**
```powershell
Get-ADUser -Filter "UserPrincipalName -eq '<upn>'" -Server "<managedDomainFQDN>" -Properties whenCreated,PasswordLastSet
```
Expected: object exists, `PasswordLastSet` is populated (not null). A missing `PasswordLastSet` on a cloud-only account means the user has never changed their password since Domain Services was enabled — no hash exists to sync yet.

**Step 5 — Confirm lockout/enabled state INSIDE the managed domain (not Entra ID)**
```powershell
Get-ADUser -Identity "<sAMAccountName>" -Server "<managedDomainFQDN>" -Properties LockedOut,BadLogonCount,AccountLockoutTime
```
Expected: `LockedOut: False`. Remember this state is **entirely local** to the managed domain — Entra ID's own risk/lockout signals are unrelated and won't show this.

## Common Fix Paths

<details><summary>Fix 1 — User exists in Entra ID but not (yet) in the managed domain</summary>

**Cause:** Either sync hasn't completed (can take hours on first enablement, minutes for incremental changes after), or — for a cloud-only account — the user has never changed their password since Domain Services was turned on, so no NTLM/Kerberos hash was ever generated to synchronize.

```powershell
# Confirm account type and force the password-change trigger for cloud-only users
Get-MgUser -UserId "<upn>" -Property OnPremisesSyncEnabled
# If OnPremisesSyncEnabled is $null/False, this is a cloud-only account:
Update-MgUser -UserId "<upn>" -PasswordProfile @{ ForceChangePasswordNextSignIn = $true }
# Have the user sign in and change their password — this triggers hash generation

# For hybrid accounts, verify Entra Connect has completed a full sync and PHS is current
# (run on the Entra Connect server)
Start-ADSyncSyncCycle -PolicyType Delta
```

**Rollback note:** Forcing a password change is non-destructive but user-visible — warn the help desk before doing this in bulk.

</details>

<details><summary>Fix 2 — Account locked out in the managed domain only</summary>

**Cause:** 5 bad password attempts within 2 minutes locks the account for 30 minutes, evaluated entirely inside the managed domain. This has zero effect on — and zero visibility from — the account's Entra ID state.

```powershell
# Confirm lockout, then either wait out the 30-minute window or unlock explicitly
# from a management VM domain-joined to the managed domain
Get-ADUser -Identity "<sAMAccountName>" -Server "<managedDomainFQDN>" -Properties LockedOut
Unlock-ADAccount -Identity "<sAMAccountName>" -Server "<managedDomainFQDN>"
```

**Rollback note:** N/A — unlocking is non-destructive. If lockouts recur frequently for one account, consider a custom fine-grained password policy (see `-A.md` Playbook) rather than repeatedly unlocking.

</details>

<details><summary>Fix 3 — Sign-in fails with SAMAccountName but the account is otherwise healthy</summary>

**Cause:** `SAMAccountName` is sourced from `mailNickname` and gets **autogenerated** (not matching what the user expects) when there's a `mailNickname` collision across users, or when the UPN/mailNickname prefix exceeds the 20-character `SAMAccountName` limit.

```powershell
# Confirm the actual (possibly autogenerated) SAMAccountName
Get-ADUser -Filter "UserPrincipalName -eq '<upn>'" -Server "<managedDomainFQDN>" -Properties SamAccountName

# Standing fix: always instruct users/scripts to sign in with UPN format
# (user@domain.com), never DOMAIN\username — UPN is the only reliably stable identifier
```

**Rollback note:** N/A — this is a standing operational guidance fix, not a reversible change.

</details>

<details><summary>Fix 4 — Managed domain's auto-created NSG was modified</summary>

**Cause:** Someone added, removed, or edited a rule on the platform-managed NSG attached to the managed domain's subnet. This is explicitly unsupported and can silently break synchronization, patching, and Microsoft's ability to manage the domain — often well before any user notices an authentication failure.

```powershell
# Compare current rules against the required baseline
Get-AzNetworkSecurityGroup -Name "<managedDomainNsgName>" -ResourceGroupName "<rg>" |
  Select-Object -ExpandProperty SecurityRules | Format-Table Name, Access, Direction, DestinationPortRange

# Required inbound: AllowVnetInBound, AllowAzureLoadBalancerInBound (defaults),
#   plus AzureActiveDirectoryDomainServices -> TCP 5986 (WinRM, required)
#   plus CorpNetSaw -> TCP 3389 (RDP, optional — MS support only, can only be
#   added/edited via PowerShell, not the portal)
# Required outbound: 443 to AzureActiveDirectoryDomainServices, AzureMonitor,
#   Storage, AzureActiveDirectory, GuestAndHybridManagement service tags

# If a custom rule was added, remove it and let the platform-managed baseline stand
Remove-AzNetworkSecurityRuleConfig -Name "<customRuleName>" -NetworkSecurityGroup $nsg
$nsg | Set-AzNetworkSecurityGroup
```

**Rollback note:** Removing an incorrect custom rule is safe. Do not attempt to recreate the platform's own default rules manually — if they were deleted, engage Microsoft support; the Azure SLA explicitly does not cover deployments broken by a misconfigured NSG.

</details>

<details><summary>Fix 5 — Active alert on the managed domain (Health blade)</summary>

**Cause:** Varies — common alerts include DNS misconfiguration on the VNet, an expired/near-expiry KRBTGT-adjacent condition, replica set connectivity loss, or an outbound NSG rule silently blocking replication between DCs.

```powershell
# Check health status and resolve the specific alert via its documented remediation
# (Entra admin center: Entra ID > Domain Services > <domain name> > Health)
# Do not proceed with per-user troubleshooting until active alerts are cleared —
# most sign-in symptoms downstream of a live alert are noise, not the real issue
```

**Rollback note:** N/A — alert remediation is domain-specific; follow the exact resolution steps shown against each alert type in the portal.

</details>

<details><summary>Fix 6 — Restored (recycle-bin) user lost access to previously-owned resources</summary>

**Cause:** When a user is deleted in Entra ID, the deletion syncs to the managed domain immediately (no recycle bin exists there). If later restored in Entra ID, the user re-syncs to the managed domain as a **new object** with a new GUID and SID — any ACLs on managed-domain-joined resources that reference the old SID are now orphaned.

```powershell
# Confirm the user's CURRENT SID in the managed domain
Get-ADUser -Filter "UserPrincipalName -eq '<upn>'" -Server "<managedDomainFQDN>" -Properties SID

# Re-apply NTFS/share/application ACLs using the new SID/account — there is no
# automatic re-linking of the old permission entries
```

**Rollback note:** N/A — the SID change itself can't be reversed; only the downstream ACLs can be repaired.

</details>

<details><summary>Fix 7 — Enabling Domain Services fails with a named stale-application error</summary>

**Cause:** A leftover `Microsoft Entra Domain Services Sync` enterprise application, or an `AzureActiveDirectoryDomainControllerServices` app registration (AppId `d87dcbc6-a371-462e-88e3-28ad15ec4e64`) from a prior failed or deleted deployment attempt is blocking a clean re-enable.

```powershell
$aadDsSp = Get-MgServicePrincipal -Filter "AppId eq 'd87dcbc6-a371-462e-88e3-28ad15ec4e64'" -ErrorAction Ignore
if ($aadDsSp) { Remove-MgServicePrincipal -ServicePrincipalId $aadDsSp.Id }

$identifierUri = "https://sync.aaddc.activedirectory.windowsazure.com"
$app = Get-MgApplication -Filter "IdentifierUris eq '$identifierUri'"
if ($app) { Remove-MgApplication -ApplicationId $app.Id }

$sp = Get-MgServicePrincipal -Filter "ServicePrincipalNames eq '$identifierUri'"
if ($sp) { Remove-MgServicePrincipal -ObjectId $sp.Id }

# Also confirm the Microsoft Graph app (AppId 00000002-0000-0000-c000-000000000000)
# is enabled for sign-in — Domain Services enablement requires it
```

**Rollback note:** Deleting these specific stale app registrations is the documented Microsoft-supported remediation and is safe — they hold no live configuration once the original enablement attempt failed.

</details>

## 🎓 Learning Pointers

- **Always sign in with UPN format (`user@domain.com`), never `DOMAIN\username`.** `SAMAccountName` is derived from `mailNickname` and gets silently autogenerated on collision or length overflow — UPN is the only identifier guaranteed to match what's in Entra ID.
- **Lockout, password expiry, and "enabled" state are all evaluated locally inside the managed domain, completely independent of Entra ID's own state for the same user.** Never trust Entra ID's view when diagnosing an authentication failure against the managed domain — always query `Get-ADUser` against the managed domain FQDN directly.
- **A brand-new cloud-only user is invisible to the managed domain until they change their password at least once after Domain Services was enabled** — this is the single highest-frequency "why can't this new hire domain-join their VM" ticket, and the fix is a forced password change, not a sync retry.
- **Never edit the auto-created NSG, load balancer, or public IP on the managed domain's subnet.** These are platform-managed; unsupported changes can silently break sync, patching, and Microsoft's own management access, and the Azure SLA explicitly excludes outages caused by a misconfigured NSG or route table.
- **Guest/B2B and other external-directory accounts can never sign in to the managed domain** — Domain Services has no access to their credentials (Entra ID doesn't store passwords for them), and there is no configuration fix, only conversion to a native member account.
